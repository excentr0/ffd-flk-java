# ФФД 1.05 / 1.1 / 1.2: структурированные данные источников

**Статус: проверяемое извлечение и кандидаты AST; не сертифицированная база исполняемого ФЛК.**

В `ffd-*.json` действительно заполнены каталоги, документные поля, вложенные пути и строки логического контроля. Это не прежний сырой каркас с пустыми массивами. Однако полная нормативная трактовка и применимость логических таблиц к ККТ → ОФД не утверждены: `readiness.production_ready=false`, `semantic_review.status=pending`, все логические AST неисполняемы.

| ФФД | Редакция протокола | PDF-страниц | Тегов с определениями в таблицах | Контекстных записей полей |
|---|---:|---:|---:|---:|
| 1.05 | 9.8 | 151 | 110 | 334 |
| 1.1 | 3.8 | 195 | 138 | 829 |
| 1.2 | 2.15 | 222 | 185 | 903 |

Повтор одного номера тега в разных документах/контейнерах сохраняется. В словаре отдельно могут быть `reference_only_not_a_field_definition`: номер упомянут правилом, но его определения в таблицах нет. Это **не** выдуманное определение и не дополнительно доказанный тег. `code` — дискриминатор документа, не TLV-тег; `tag_numbers` и `tag_path` у него пусты.

## Формат

- `source`: исходный файл, SHA-256, версия; PDF — окончательное свидетельство.
- `pages`: полный PDF-текст, исходные обнаруженные таблицы, ячейки и координаты таблиц. Содержатся также общие разделы, приложения и история изменений.
- `documents`: восемь групп документов, таблицы 14/16/18/20/22/24/26/28, исходные поля, `parent_field_id`, `tag_path`, raw обязательность/тип/значение/длина/коды и ссылки.
- `tags`: индекс вхождений; глобальный тег **не** имеет универсальной обязательности/длины.
- `row_ledger`: каждый классифицированный физический фрагмент форматных и парных логических таблиц 14–29. Исходные `raw_cells` не переписываются. Продолжения связываются через `record_id`.
- `rules`: кандидатные форматные ограничения для неосвобождённых документов и записи парных логических таблиц ППФД. Их количество — не доказанное количество всех самостоятельных нормативных проверок.
- `formalization`: структурированные ограничения и синтаксические AST. Нормализованный текст и преобразование сохраняются. `condition/check/description` рассматриваются совместно; parsed ≠ approved ≠ executable.
- `notes`, `general_requirements`, `revision_statements`: текст с контекстом, не автоматически утверждённая привязка примечаний к правилам.
- `unresolved`: неподдержанные выражения, неутверждённая кратность, конфликты иерархии и ссылочные теги. Нельзя скрывать их или считать PASS.

`source_refs.page` — номер физической PDF-страницы (1-based); `fragment_index`/`physical_row_index` — исходные таблица/строка на странице. Длинная строка может иметь несколько ссылок. Для объединённых условий указаны `condition_cell_origin` и, при разделении двух ИНН-проверок, `row_y_interval`.

## Три разных проверки

1. `verify.py` повторно читает исходный PDF, сверяет хеш, страницы, текст, таблицы и их bbox. Это **same-library integrity**, не независимая семантическая проверка.
2. `verify_semantics.py` независимо получает расположение заголовков через **Poppler bbox XML**, определяет принадлежность фрагментов таблицам и проверяет порядок всех пронумерованных строк обнаруженных форматных сеток, листовые теги, связи и сохранение ячеек. Это источник-ориентированная проверка учёта строк, но обнаружение самой сетки всё ещё происходит через pdfplumber. Полнота обнаружения сеток/всех логических строк и визуальная правильность объединений этим не доказаны.
3. Семантическая готовность требует независимой визуальной сверки условий, кванторов, единиц, кодов, примечаний, области входного ФЛК и формализации каждого применимого правила. Сейчас **0 семантически утверждённых / 0 исполняемых логических правил**.

`coverage.json` содержит фактические результаты, а не обещание 100%. `--require-ready` намеренно завершается ненулевым кодом для этого комплекта. Неполнота базы блокирует утверждение готовности валидатора, **не служит основанием отказать конкретному ФД**. Сверка исходных вложенных кодов и физических ячеек через Poppler, визуальные спорные случаи и исправление кода 536 в ФФД 1.1 p.43 описаны в [отчёте](../../review-evidence/pdf-audit.md).

### Найденные особенности источников

- §4, PDF-страница 11 всех трёх протоколов, освобождает регистрацию и изменение регистрации от входного ФЛК. Наличие таблиц ППФД не отменяет исключения.
- §3: отсутствующий/иной 1209 может означать другой маршрут, а не отказ.
- ФФД 1.1 содержит дубли ordinal в колонке номера тега.
- ФФД 1.2 содержит несовпадения печатной нумерации и именованных STLV-путей: например, таблица 22, PDF-страница 63, `38.25` — лист 1265, а `38.25.1` — корневой контейнер `properties` 1084. Сохранены обе исходные формы и флаг конфликта; требуется визуальное утверждение.
- В ФФД 1.05 таблица 29 кодовая ячейка объединяет 502/503/536. Использовано чтение кода в y-интервале проверки; соответствие необходимо независимо проверить визуально.
- Regex, единицы денег/времени, внешние алгоритмы, суммирование и округление не заменяются догадками. Неисполняемый кандидат сохраняет raw.

## Воспроизводимость

Нужны Python 3, `pdfplumber`, `jsonschema`, Poppler (`pdftotext`). Исходные файлы включены в `sources/`; соседний проект документации не требуется. Следующие команды выполняются из `references/data/`.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/extract.py
.venv/bin/python scripts/normalize.py
.venv/bin/python scripts/formalize_data.py
.venv/bin/python scripts/verify.py
.venv/bin/python scripts/verify_semantics.py
.venv/bin/python -m unittest discover -s tests -v
for v in 1.05 1.1 1.2; do
  .venv/bin/python scripts/audit_nested_codes.py --version "$v"
  # При несовпадении команда завершается ненулевым кодом; проверь каждую
  # строку mismatch по PDF и по review-evidence/pdf-audit.md.
  .venv/bin/python scripts/audit_logical_cells.py --version "$v"
done
# Ожидаемый ненулевой результат: полная семантика пока не утверждена.
.venv/bin/python scripts/verify_semantics.py --require-ready
```

`--output-dir` у extract и `--dataset-dir` у normalize/formalize/verify позволяют работать в временном каталоге. `verify_semantics.py --source-root DIR` явно выбирает оригиналы. До первого шага сохранить нужный комплект: raw extract заменяет нормализованные данные и требует последующих normalize/formalize. Результаты полной пересборки нужно проверять заново.

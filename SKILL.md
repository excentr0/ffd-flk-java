# ФЛК фискальных документов на Java

## Задача и границы

Пиши ФЛК **ККТ → ОФД**, а не механическую копию проверок ППФД на стороне ФНС. Поддерживаются отдельные наборы правил ФФД **1.05**, **1.1**, **1.2**. Номер версии документа протокола не является номером ФФД.

Приоритет: **достоверность источника → корректность проверки → полнота → производительность**. Не добавляй «разумную» проверку, отсутствующую в подтверждённом правиле. Не ослабляй явно установленную проверку ради удобства.

## Сначала прочитай данные

Пути разрешай относительно каталога этого SKILL.md, не cwd проекта.

1. Прочитай `references/source-policy.md` и `references/java-validation.md`.
2. Найди базу в `references/data/`. Прочитай её `README.md`, `coverage.json` и `schema.json`.
3. Для требуемой версии открой `ffd-1.05.json`, `ffd-1.1.json` либо `ffd-1.2.json`. Выбери записи нужного документа и **контекста вложенности**, не загружай все PDF в контекст без необходимости.
4. Комплект автономен: база и первичные источники находятся в `references/data/`. Если встроенная база отсутствует, комплект неполон; это не доказательство валидности документа.
5. Перед использованием проверь контрольные суммы, результаты проверки, [PDF-аудит](review-evidence/pdf-audit.md) и все `unresolved`/статусы. Покрытие сохранения исходных страниц не доказывает семантическую полноту правил.
6. Если нет базы, данных нужного контекста или подтверждения трактовки — сообщи, чего не хватает. Не замени их знаниями из памяти.

В каждой реализации фиксируй версию ФФД, редакцию протокола, хеш источника и границу применимости. Обновление данных — отдельная проверяемая операция, не автоматическая подмена действующей политики.

## Текущий комплект и схема

Встроенные JSON **не пусты**: 334/829/903 контекстные записи полей и 110/138/185 тегов с определениями соответственно. Это не доказательство полной семантической готовности: сейчас 0 утверждённых исполняемых логических правил. Не повторяй устаревшие отчёты о пустых `tags/documents/rules`; проверяй фактические файлы и `coverage.json`.

- Выбирай `documents[].fields` по документу и `tag_path`; `tags[].occurrences` — лишь индекс.
- `field_kind=document_discriminator` (`code`) и `non_tlv_source_field` не являются TLV-тегами. Число из исходной дублированной ordinal не декодировать как тег.
- `printed_hierarchy_conflict` и `parent_evidence` требуют чтения именованного контейнера/STLV и оригинала; нельзя вернуть корневой 1084 под лист 1265 из-за печатной нумерации.
- Кандидат `cardinality.maximum=1` со статусом `minimum_source_literal_maximum_requires_policy_review` не является утверждённым singleton. Не назначай 424 без проверки повторяемости и примечаний.
- Логические `formalization.condition/check.ast` — только синтаксис. Аннотация `path[].tag` ещё требует привязки к исходному полю/контексту; особенно `code` и внешние переменные не становятся TLV по числу в скобках.
- Читай `raw`, `source_refs`, `condition_cell_origin`, `row_ledger` и связанные `unresolved`. Даже отсутствие структурных ошибок не разрешает исполнять pending-правило.
- Источник конкретного поля можно независимо утвердить для конкретной реализации, сохранив доказательство и тесты. Не требуется запрещать безопасный Java-пример механизмов из-за неполной базы: маркируй его как механизм, не полный нормативный валидатор.

Для просмотра конкретного контейнера без загрузки всего JSON в контекст:

```sh
python3 references/data/scripts/query.py --version 1.2 --document receipt --tag 1224
```

Проверь `references/data/SHA256SUMS.txt`, исходные PDF в `references/data/sources/`, затем integrity и source-accounting проверки из README. Gate `--require-ready` пока должен завершаться ненулевым кодом.

## План и критерии готовности

Перед изменениями выясни Java/build/test версии и представление входа: исходные TLV/STLV байты, список узлов или уже нормализованная модель. Уточни, сохранены ли повторяющиеся теги, исходная длина, порядок и положение узла. `Map<Integer,Object>` не подходит, если уничтожает повторы или контекст.

Составь таблицу трассировки:

`rule_id | version | document | parent_path | source_page/table/row | applicability | violation | code/severity | implementation | positive/negative/boundary tests | status`

Каждую релевантную исходную запись классифицируй как реализованную, исключённую по подтверждённой области применения, зависимую от внешнего контекста либо блокирующую уточнение. Не выпускай «полный ФЛК», если есть незакрытые обязательные правила.

## Применимость прежде проверки

- Не смешивай проверки полученного от ККТ документа, обработанного представления для передачи в ФНС и ответа ППФД.
- Прочитай §3 и §4 **конкретной версии** и исключения для вида документа. В приложенных трёх редакциях §4 (PDF-стр. 11) **прямо освобождает** отчёт о регистрации и отчёт об изменении параметров регистрации от ФЛК входного ФД. Наличие таблиц ППФД с обязательными тегами не отменяет освобождение.
- Освобождение от ФЛК не отменяет безопасного разбора контейнера, аутентификации ФН и проверок транспорта, явно применимых к этому этапу.
- Определение/маршрутизация версии по тегу 1209 — отдельное правило. Его отсутствие не означает безусловную ошибку во всех документах.
- Для правил с `receiveDateTime` в ППФД не подставляй автоматически время приёма в ОФД: это разные события.
- Фискальный признак, договор, статус ККТ, история смены и документы прошлого периода требуют внешнего контекста/криптографической проверки. Не выдавай проверку длины за проверку подлинности.
- При недостатке контекста возвращай «проверка не выполнена/требуется контекст», не «документ корректен» и не «документ некорректен».

## Структура и реквизиты

- Выбирай ограничения по `(version, document, parent_path, tag)`. Один номер тега не задаёт универсальную обязательность, длину и допустимость.
- Сохраняй **все вхождения** тегов. Повторяемость проверяй в пределах указанного родительского STLV, отдельно для каждого экземпляра контейнера.
- Различай отсутствующее поле, пустое значение, null в модели, ноль и false. Не считай необязательные числовые реквизиты нулевыми без правила источника.
- Сохраняй дословную обязательность, включая условные выражения и обозначения `0`, `1`, `x`, `1...n`. Переводи в cardinality/применимость только после проверки определения обозначений и примечаний.
- Не выводи родительский TLV-путь только из похожего JSON имени; проверь контейнер/таблицу/исходный STLV. Учти кириллические/латинские двойники и переносы строк в PDF.
- Проверяй тип, диапазон и **байтовую длину в исходной кодировке**, а не `String.length()` вместо длины TLV. Для `REG_BITS_*` отдельно проверь определение регистра и допустимые комбинации: список битовых флагов нельзя автоматически принять за список разрешённых целых значений или за условие `mask != 0`.
- Длина значения STLV включает заголовки и значения всех дочерних TLV; не включает собственный заголовок. Дополнительно сохраняй и проверяй предел внешнего контейнера.
- Тип/длина ошибочного необязательного тега не должны превращаться в код ошибки обязательного тега. Сохраняй исходные коды и категорию; код ошибки сам по себе не уникальный ID правила.
- Отклонение неизвестного тега, превышение длины и недопустимый повтор — разные ошибки. Не вводи общую политику «запретить неизвестные» вместо конкретного правила версии/документа.
- Условия для вложенного тега исполняй с правильным квантором и областью: текущий предмет расчёта, все предметы, любой предмет, сумма по контейнеру. Нельзя проверять поставщика одного предмета по тегу другого.

## Формальные правила

Извлечённые строки условия/проверки — свидетельства, а не готовый код. Исполняй только подтверждённый AST. Читай одновременно condition, check, description, примечания и source_ref.

`applicable(context) && violation(document, context)` означает ошибку. Не инвертируй смысл столбца «Проверка». Нельзя исполнять произвольные строки через eval, скриптовый движок или генерировать Java без проверки AST.

Неразобранное выражение, конфликт столбцов, обрыв продолжения таблицы, отсутствующая единица измерения или неоднозначный квантор — **блокер реализации соответствующей проверки**. Сохрани исходный фрагмент и вопрос. Не выдай stub/always-true/always-false за реализованный контроль.

Неполная база не является доказательством неправильности ФД: блокируй утверждение полноты/ввод валидатора в эксплуатацию, а не выдумывай основание для отказа конкретной кассе.

## Java

Следуй `references/java-validation.md`. Используй библиотечный разбор/существующую модель проекта, если она не теряет сведения. Не добавляй Spring/Quarkus, базу данных или движок правил ради одной библиотеки ФЛК.

Предпочитай неизменяемые описания правил и локальную коллекцию ошибок. Для повторных проверок документа однократно индексируй теги **в каждом контейнере**; не сканируй весь документ заново для каждого правила. Никакого сетевого I/O, чтения JSON и компиляции regex на каждый документ. Не жертвуй точными decimal/unsigned вычислениями ради оптимизации.

## Обязательные тесты

Для каждой применимой проверки: допустимый пример, нарушение, обе границы, неприменимое условие, отсутствие/пустота/ноль, вложенность/повтор — где соответствуют правилу. Для формулы нужны точная граница допуска и превышение на минимальную единицу. Для даты — границы месяца/года, часовой пояс и фиксированный Clock/контекст.

Отдельно проверь:
- регистрацию/перерегистрацию против исключений §4;
- идентичные теги в разных вложенных контейнерах и версиях;
- повтор singleton в одном контейнере и разрешённый повтор контейнеров;
- длинную строку, для которой число символов и байтов различается;
- UInt64 выше Long.MAX_VALUE и арифметическое переполнение;
- отсутствие необходимых внешних сведений;
- неполную формализацию/конфликт источника — нельзя получить итог «все проверки пройдены»;
- коды, категории, сообщения и детерминированный порядок результатов.

Запусти проверку базы, компиляцию и тесты проекта. Укажи фактически выполненные команды. Независимое ревью должно сравнивать код с источником, а не только с ожидаемыми результатами собственных тестов.

Кратко перечисли реализованные правила/версии/документы, результаты тестов и незакрытые вопросы. Приложи таблицу трассировки. Не обещай «все теги/100% корректность», если доказано лишь совпадение списков номеров тегов или сохранение текста PDF.
